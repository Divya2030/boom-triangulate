A load may miss a needed replay

A load that took its value from an older store may need to run again if a store in between works out its address later. That replay can be missed.

Load-load ordering may not be flagged

A younger load that ran early is only flagged as an ordering problem when the line's observed bit is set during the load search. If it is not, the check is skipped.

Planted-bug study

complete · Spike + Dromajo + BOOM

Real bugs in a mature core are rare, so we test the loop against planted bugs — one small, reversible change per spot, each a known bug. That turns the evaluation into two numbers: recall (seeds caught) and triage precision (RTL_DEFECT verdicts that land on a real seed). Recall counts only observable seeds: a defect that never changes committed state can't be caught by any differential test, and is reported as such rather than scored as a miss.

Random-program campaigns

integer + floating-point · Spike + Dromajo + BOOM

Targeted tests aim where we chose. To cover ground we did not choose, we also ran many constrained-random programs — every one legal, terminating, and trap-free, so a difference is a real disagreement, not a crash we caused. The integer runs came first; then we turned on the FPU and aimed a second generator at the parts of floating point that go wrong most.

The floating-point generator targets the hard seams: NaN-boxing, min/max with a NaN, saturating float→int, signed zero, fused multiply-add, and all five rounding modes. One trick keeps the vote sound — the three models print float registers differently, so we never compare them directly. Each result is moved into an integer register (fmv.x.d) and the exception flags read into one (csrr fflags), so every value lands in the integer file, which all three log the same way.

TEST-SETUP · caught twice

Two false alarms the triage refused to ship

During bring-up the vote twice called BOOM the outlier. Both were our own start state, not BOOM. First the exception-flag register: BOOM powers up with bits set that the references start clear, so a test that never cleared it was comparing leftover reset state. Then the rounding mode: a dynamically-rounded subtract differed by one unit in the last place because we hadn't set it, and BOOM's reset rounding mode differs from the references'. Clearing the whole floating-point control register first — flags and rounding mode — made all three agree. A vote proposes; the exact instruction disposes.

RTL_DEFECT · the vote wins

The second reference model found a bug the first one missed

The planted store-to-load forwarding bug threw the program off course, so the difference looked like a cut-off trace — which a single reference model reads as a test-setup problem and misses. The vote caught it: both references finish and agree, BOOM is the odd one out, so it is a BOOM bug no matter how the difference looks. This is the clear reason to use two references.

The two entries below are the decide step doing its job — refusing to call a non-bug a bug. No new, real BOOM bug has been found yet; the win above is on a planted bug.

HARNESS_ARTIFACT · resolved

A logging habit that looked like a bug

BOOM logs the trapping ecall/c.ebreak with no register write; Spike jumps straight to the handler. Both reach the same handler with the same mcause, so the state is the same. We handle it, but we count and report each skip instead of quietly realigning — a tool that quietly realigns can hide a real bug.

HARNESS_ARTIFACT · resolved

An empty trace from a wrong file path

A wrong file path made BOOM produce an empty trace. The decide step correctly refused to call an empty trace a bug, and told "the tool did not run" apart from "the models disagree." This is why we run fixed checks before any model call.

Ideas to extend the loop

each builds on existing work
triage · a third reference two built

Add a formal reference model

The vote with Spike and Dromajo is built and working. Adding the Sail formal RISC-V model as a third reference would make it stronger, since Sail is the official written spec. ProcessorFuzz found a real bug in a reference model, so a third view helps.

refs Sail (POPL'19) · ProcessorFuzz
hypothesize · feedback

Use coverage to aim the tests

Right now the loop reads only the source. Feeding it live signals — CSR changes (ProcessorFuzz) or register coverage (DIFUZZRTL) — would tell the model where the tests have not been yet.

refs ProcessorFuzz · DIFUZZRTL
generate · reachability

Write deeper test programs

Straight-line programs can't reach every state. Cascade-style tangled programs reach much deeper, which would make more planted bugs observable and raise the recall ceiling.

refs Cascade (USENIX'24)
generate · reachability

Build a richer harness

Most documented BOOM bugs live behind virtual memory, a change of privilege, or a second core — which this bare-metal single-core harness does not set up. A harness that builds page tables, steps through privilege levels, and boots more than one hart would let the same vote reach those bug classes. This is the change most likely to turn the method from catching planted bugs into finding real ones.

refs BOOM issues · RISC-V priv. spec
triage · escalation

Prove a difference with a formal check

A difference found by testing is a cheap lead; a bounded formal check is a proof. A found difference could seed a formal property, checked by the yosys/SymbiYosys flow we built earlier, to turn a suspect trace into a proof or a small counterexample.

What this shows, and what it doesn't

  • The results are from planted bugs, not a new BOOM bug. They show the method works — it finds bugs we put in on purpose. We have not yet found a new, real bug in BOOM.
  • Some planted bugs are not observable on one core. Three of the eleven never change what a single core commits, so no comparison can catch them. Two of those need more than one core; the third our tests never trigger. We leave them out of the recall number instead of counting them as misses.
  • The reference models agree with each other, except one logging habit. On the exception test Spike and Dromajo differ, but it is only how they log a trap, not a real disagreement — and the tool does not call it a bug.
  • We credit what is not ours. Running Spike next to BOOM is a Berkeley feature. What we add is choosing the tests, writing them, and deciding what each difference means.
